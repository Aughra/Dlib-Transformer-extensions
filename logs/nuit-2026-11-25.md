## Décisions prises cette nuit

### Chantier 1 — KaTeX retiré (Gulliver 7.2.3)

- **Décision** : retrait complet (pas de « à la demande »), demande de l'humain « KaTeX on enlève ».
- **Chute visuelle acceptée** : les formules apparaissent telles qu'écrites par le modèle (`$E = mc^2$`), comme le reste du texte. Pas d'usage central pour un chat local, pas un investissement à garder pour 1 Mo.
- **Fallback** : rien d'autre à faire. marked, sans l'extension `math`, voit les `$` comme du texte, donc la réponse rend tels quels les délimiteurs.
- **Points de contact touchés** : 8 fichiers + suppression de `web/vendor/katex/` + nettoyage du build (CMake `copy_directory` n'efface pas). Détail complet dans `logs/journal-modifications.md`.
- **Gain** : vendor/ de 4,3 → 3,7 Mo (−600 Ko) ; JavaScript du fork inchangé sauf `markdown.js` (−48 lignes).

### Chantier 2 — PDF.js → PDFKit (à faire)

À décider avant de taper : PDFKit est le bon outil (il lit le texte, les positions et les signets, et fonctionne dans un processus hôte). PDFium reste dans le service pour la rétro-compatibilité tant qu'on n'a pas vérifié que les textes extraits concordent (contrôle à mettre en place).

Plan détaillé à poser dans ce fichier au début du chantier.

### Chantier 3 — Markdown → HTML côté serveur (à faire)

Deux voies possibles :
1. Un petit parseur Markdown en C++ écrit maison, inspiré de GFM, avec un ensemble réduit mais couvrant (gras, italique, listes, code, tableaux, liens, images, titres, HTML inline nettoyé).
2. Embarquer une bibliothèque C++ existante (md4c, cmark-gfm). Choix facile côté licence (MIT / CC0).

Choix à poser : maison (pour l'indépendance, règle du fork) ou bibliothèque (pour la fiabilité et le temps). Je décide au début du chantier.

Difficulté connue : le streaming. Le serveur reçoit des tokens au fil de l'eau ; rendre du HTML sûr d'un markdown incomplet demande soit d'attendre les fins de bloc, soit de laisser les listes et les blocs ouverts (et de fermer côté client au dernier fragment).

### Chantier 4 — Coloration du code maison (à faire)

Approche prévue : tokenizer par langage. Commence par les langages que le chat voit le plus : Python, C, C++, JavaScript/TypeScript, Rust, bash, et un fallback générique. Classes CSS compatibles `hljs-*` (pour ne pas toucher au CSS actuel).
